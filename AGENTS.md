# Редактирование файлов
- ОБЯЗАТЕЛЬНО перед каждым планированием ИЛИ изменением перечитывать актуальную версию редактируемого файла/скрипта (файл могут править вручную между запросами). Не полагаться на контент из прошлых сообщений/контекста — не вносить правки вслепую, всегда сверяться с текущим состоянием файла на диске.

## Стиль SQL-скриптов

- все ключевые слова и имена в **lower case**
- запятая ставится **на следующей строке** (перед полем), а не после предыдущего поля
- не оставлять пустых строк без комментариев — каждая пустая строка должна содержать `--`
- отступы выравнивают колонки визуально (пробелы до `as`, `from`, `where` и т.д.)

# Использование готовых скриптов или написание кода на основе примеров 
- Всегда использовать найденные куски кода в точности, не добавляя функциональности / комментариев / тестов если нет четких указаниев это сделать или это не требуется поставленной задачей; Лучший инструмент для этого - **rag репозитория rag code oper smkt по mcp**
- При создании шаблонов кода оставляй минимальную функциональность - шаблон это точка старта, а не то, откуда нужно будет удалять ненужное
- Каталог готовых кусков кода (подключения к БД, чтение/запись, типовые SQL-запросы): `ai/prompts/30_knowledge/code_snippets_guide.md`
- Перед написанием шаблонного кода (импорты, параметры подключения, read/write, типовые запросы) — искать готовый кусок в этом каталоге и использовать его в точности.

# Поиск папки/файла в определённом месте
- Если требуется найти, сохранить или изменить какой-то файл в определённом месте, использовать следующий порядок поиска папки:
  1. полное совпадение в текущей директории;
  2. частичное (по подстроке);
  3. рекурсивное вниз по иерархии папок — точное совпадение;
  4. частичное рекурсивное вниз по иерархии папок.
- Если при частичном совпадении выдается несколько вариантов — всегда спросить у пользователя, какой вариант использовать.

# Выполнение кода и запросов к бд
- Никогда не запускать запросы к БД без четких указаний на это.
- Всегда проверять набор навыков / mcp для запросов к бд и использовать их вместо исполняния запросов и shell
- При ошибке навыка / mcp по работе с бд сделать один ретрай. При повторной ошибке суммаризировать и отдать пользователю, не пытаться фиксить инструменты / креды / иное, что не относится к задаче.

# Источники данных
- Единая справка по источникам данных (слои, таблицы, ключи ЦФЗ, часовые пояса, подводные камни): `ai/prompts/30_knowledge/data_sources_guide.md`
- Перед выбором таблиц / join / фильтров — сверяться с этим гайдом и следовать его правилам (ключи слоёв, `lower()`, `::date`, регистр констант, TZ).
- Если нет информации о поле/таблице, воспользоваться навыком по получению ddl таблицы.

# Дополнение гайда по источникам данных
- При обнаружении любых новых сведений о данных (новая таблица, поле, схема, ключ, особенность TZ/регистра, источник отмен/прогноза/заглушек) — обязательно дополнять `ai/prompts/30_knowledge/data_sources_guide.md` в соответствующем разделе (1–9).
- Не промолчать про нюанс, если он пригодится в других задачах:
  1) Был найден источник/поле для ранее «не найденного» пункта → снять пометку `⚠ не найдено`, указать таблицу и прокси.
  2) Справочник нового слоя / новый внешний источник → добавить строку в каталог соответствующего раздела.
  3) Новая строка-константа, часовой пояс или изменение схемы → дополнить таблицы в разделе 9 «Общие правила».
- Формат дополнений: след в стиле остальных таблиц гайда; указывать задачу (PA-номер) при заметном нововведении для трассировки.
- Обновлять `Version` (minor при добавлении строк, major при изменении правил/ключей) и `Last updated` в шапке файла.
